A.2Recovering Homographies

Each point pair gives you two equations, one for x′ and one for y′, after you multiply out the bottom row of H. For these images, I clicked 5 points by hand using the correspondence tool made by a past student, on recognizable spots in both images. Since this is an overdetermined system (10 equations for 8 unknowns), I solve it with least squares and put the 1 back in as the bottom right entry of H.

p′ = H p,   H = [ a b c ; d e f ; g h 1 ]
x′ = (a x + b y + c) / (g x + h y + 1),   y′ = (d x + e y + f) / (g x + h y + 1)
[ x y 1 0 0 0 −x x′ −y x′ ] h = x′

A.3Warping the Images

We're using inverse warping for this assignment. So first, we apply our homography to the four corners of the image to figure out the size of the output. Then for every output pixel, you use the inverse of your homography to figure out where it came from in the original, which lets you avoid holes in your output image. For nearest neighbor interpolation, we just take the closest pixel, and bilinear takes the weighted average of the four closest pixels, which leads to a pretty sizable difference in images between the two.

For rectification, all I did was click the four corners of the bulletin board and MLK sign, then map them to a rectangle. It's fairly straightforward, and our warping made it look like you're standing right in front of them pretty well. The interpolation still mattered for readability, though.

When you zoom out, both bilinear interpolation and nearest neighbor interpolation look about the same. Once you zoom in on different parts of these images, nearest neighbor gets very blocky and jagged, while bilinear is a lot smoother. Bilinear is noticeably slower on our images, since it has to read 4 pixels for every output pixel instead of 1. Both methods get slower with the size of the output, since we have to go through the loop once for every output pixel. Bilinear is definitely a vast improvement quality-wise.

for every output pixel p′:   p = H−1 p′,   then sample the image at pbounding box from the four corners pushed through H; pixels that land outside the image stay empty (mask)
I(x, y) = (1−dx)(1−dy) I00 + dx(1−dy) I10 + (1−dx) dy I01 + dx dy I11bilinear; nearest neighbor just rounds x and y

A.4Blending into a Mosaic

Here we apply our inverse warp to create mosaics. Given two images, we keep one static and warp the other one into its frame, using bilinear interpolation. Then we can blend the images together, where each image gets a weight at every pixel equal to the distance to the nearest edge of that image. So a pixel in the middle of an image is highly valued, and a pixel at the edge is barely valued at all. The mosaic is then the weighted average of the two, which avoids any hard seams.

I mostly chose buildings for my mosaics, and used two-photo mosaics for the outside of Gateway and Weill Hall. I also took a four-photo mosaic of the inside of Gateway. The first two came out pretty clean, it's hard to see much ghosting. But the inside of Gateway has quite a few high frequency features, like the bars on the walls and the railing right in front of me, and I had some small movements of my phone between rotations that caused some parallax.

mosaic = (w1 I1 + w2 I2) / (w1 + w2)w = distance to the nearest edge of that image (0 outside it)

Picking points between these was honestly quite difficult. It's hard to keep track of the features you're choosing across multiple images, and you try to only have overlap between one image and its neighbors, but sometimes that's hard. I tried to mostly pick points that were far away in the scene to get more stable alignments, because the parallax from my slight motions made near objects shift more. Why Feathering

These images look quite bad without feathering. In the Weill Hall example, the sun made the two images expose differently, so with no blending or even a plain average, you just get a hard seam, while feathering smooths it into one gradient.

B&WBells & Whistles: Cylindrical Mapping (CS280A)

For the cylindrical version I put each photo on a cylinder with radius f before stitching. It's inverse sampling again, for every pixel in the final mosaic I work out its angle on the cylinder, θ = (x − cx) / f, and look up where that lands in the original flat photo. So every pixel gets sampled once, straight from the original, and I never warp something that's already been warped. I move the clicked points onto the cylinder too, and then line the two photos up with a small rotation plus a shift, and blend with the same distance weights as before.

For f I used 1110, which is the real focal length of the phone. I shot everything on an iPhone 17 Pro Max at 1x, which is a 24 mm equivalent lens, and at 1200 x 1600 that works out to about 24 / 43.3 x 2000 ≈ 1110 px. Compared to the planar mosaics, I think the cylindrical ones look a lot more natural, the warped side doesn't get stretched out. The tradeoff is straight lines like the roofline come out curved.

θ = (x − cx) / f,   xsrc = f tan θ + cx,   ysrc = (y − cy) / cos θ + cyf = 1110, the iPhone 1x lens (24 mm equivalent) at 1200 × 1600
p2 ≈ R(α) p1 + t,   α = atan2( Σ (ax by − ay bx), Σ (ax bx + ay by) )a, b = the cylinder points of each photo minus their mean; a pure pan would have α = 0

def cylinderSource(x, y, width, height, focal_length):
    cx, cy = (width - 1) / 2, (height - 1) / 2
    theta = (x - cx) / focal_length
    source_x = focal_length * np.tan(theta) + cx
    source_y = (y - cy) / np.cos(theta) + cy
    return source_x, source_y
def fitRotationShift(points1, points2):
    center1 = points1.mean(axis=0)
    center2 = points2.mean(axis=0)
    a = points1 - center1
    b = points2 - center2

    angle = np.arctan2(np.sum(a[:, 0] * b[:, 1] - a[:, 1] * b[:, 0]), np.sum(a[:, 0] * b[:, 0] + a[:, 1] * b[:, 1]))
    rotation = np.array([[np.cos(angle), -np.sin(angle)], [np.sin(angle), np.cos(angle)]])
    shift = center2 - rotation @ center1

    return np.array([[rotation[0, 0], rotation[0, 1], shift[0]],
                     [rotation[1, 0], rotation[1, 1], shift[1]],
                     [0, 0, 1]])
def cylindricalMosaic(images, transforms, focal_length):
    height, width = images[0].shape[:2]

    inverses = []
    for i in range(len(images)):
        inverses.append(np.linalg.inv(transforms[i]))

    x_min, y_min, x_max, y_max = 0, 0, 0, 0
    for i in range(len(images)):
        for corner in [(0, 0), (width - 1, 0), (0, height - 1), (width - 1, height - 1)]:
            moved = transforms[i] @ np.array([corner[0], corner[1], 1])
            x_min = min(x_min, int(np.floor(moved[0])))
            y_min = min(y_min, int(np.floor(moved[1])))
            x_max = max(x_max, int(np.ceil(moved[0])))
            y_max = max(y_max, int(np.ceil(moved[1])))

    out_height = y_max - y_min + 1
    out_width = x_max - x_min + 1
    canvases = []
    masks = []
    for i in range(len(images)):
        canvases.append(np.zeros((out_height, out_width, 3)))
        masks.append(np.zeros((out_height, out_width), dtype=bool))

    for y in range(out_height):
        for x in range(out_width):
            for i in range(len(images)):
                cyl_x, cyl_y, _ = inverses[i] @ np.array([x + x_min, y + y_min, 1])
                source_x, source_y = cylinderSource(cyl_x, cyl_y, width, height, focal_length)
                if 0 <= source_x <= width - 1 and 0 <= source_y <= height - 1:
                    canvases[i][y, x] = bilinear(images[i], source_x, source_y)
                    masks[i][y, x] = True

    mosaic = np.zeros((out_height, out_width, 3))
    total = np.zeros((out_height, out_width))
    for i in range(len(images)):
        weight = distance_transform_edt(np.pad(masks[i], 1))[1:-1, 1:-1]
        mosaic += canvases[i] * weight[..., None]
        total += weight

    total[total == 0] = 1
    mosaic = mosaic / total[..., None]

    return mosaic.astype(np.uint8)

Planar vs. Cylinder

4-Photo Atrium Panorama on a Cylinder

This is where the cylinder actually pays off. The planar Gateway atrium panorama has that bow tie shape, because on a plane the outer photos get stretched more the farther they are from the reference. On the cylinder, position is just angle, so every photo stays about the same size. I chained the rotation + shift fits the same way as the homographies, photo 1 goes through photo 2 to get to photo 3, and photo 4 uses the inverse, and then every pixel in the panorama gets sampled once straight from the original photos. It came out a lot more compact, 2191 x 1677 instead of 3146 x 2792, and I think it looks a lot more like what you actually see standing there.

First Try: Shift Only

My first version actually looked worse than the planar mosaics, there was a lot more ghosting. The idea was that if you only rotate the camera, on the cylinder the two photos just differ by a shift, so I took the median shift of the points and that was it. The problem is that assumes a perfect level pan, and I'm a human holding a phone. Between shots the phone also rolled a little, 1.4 to 2.5 degrees, and a shift can't undo a rotation. So things lined up in the middle of the overlap and drifted apart toward the top and bottom. The homography in the planar version has 8 numbers, so it just absorbed the roll, which is why the planar ones looked better.

The fix was to fit a rotation plus a shift from the same points, which is a small least squares problem, and I also switched f from 1200 to the real 1110. The table has the average error at the clicked points both ways. You can flip between them with the first try button in the viewer above. You can see it best on Weill Hall, the first version has a ghost copy of the roofline floating above the building, and in the Gateway atrium the center column is doubled. With the rotation they're both gone. There are still a few faint doubled bars on the close railing in the atrium, but that's parallax, not roll.

Part B: Feature Matching for Autostitching

B.1Harris Corners and ANMS

For corners we use the harris.py starter code. We score every pixel with our corner score, h = det(M) / trace(M), which only fires when the brightness changes in both directions, and keeps the pixels that beat their neighbors.

On my photos that gave around 49,000 corners, I sorted them by score and kept the top 3000. The problem is that the strongest corners all pile up on the trees, since leaves have edges going in every direction. ANMS fixes that. For every corner, we find the distance to the closest corner that's clearly stronger than it. Then we keep the 500 with the biggest radius. A corner just has to be the strongest thing in its neighborhood, not in the whole image, and the points end up spread out over the whole building instead of in a blob on the trees.

h = det(M) / trace(M)harris.py: corner_harris with method='eps', sigma=1; local peaks only, 20 px border dropped
ri = minj | xi − xj |   over every j with   h(xi) < 0.9 h(xj)ANMS keeps the 500 corners with the biggest r

B.2Feature Descriptors

We want a way to compare corners between photos. For each of the 500 corners, I take the 40x40 window around it and shrink it down to 8x8 by averaging each 5x5 block. The averaging also blurs it, since a blurry patch still matches when the corner is off by a pixel or two. Then we subtract the mean and divide by the standard deviation, so the same spot still matches if one photo came out brighter or with more contrast. That gives every corner 64 values to compare. These patches are aligned and only one scale, but that's fine here since I only rotated the phone between shots.

d = (p − μ) / σ,   p = 8×8 block means of the 40×40 windowflattened to 64 numbers; axis aligned, one scale

B.3Feature Matching

When matching, we compute the distance from every descriptor in photo 1 to every descriptor in photo 2, and look at the closest and second closest. If the best one is way better than the second best, it's probably a real match. If they're close, it's ambiguous, so we throw it out.

I kept a match when the ratio was under 0.7, and you can try the other values with the slider below. Under 0.6 you throw away a lot of good matches, and past 0.7 the inlier count stops going up, so you're mostly just adding bad matches for RANSAC to throw out. My distances are squared, so 0.7 here is larger on plain distances. You can still see quite a few wrong matches in the atrium, and its inlier count jumps around with the ratio, since the railing bars all look the same.

match if   e1-NN / e2-NN < 0.7e = squared distance between the 64 number descriptors (dist2 from harris.py)

B.4RANSAC and Automatic Mosaics

Even after the ratio test there are still a lot of bad matches, so we use RANSAC to pick out the good ones. Each round, I pick 4 random matches, fit an exact homography with computeH, push every photo 1 point through it, and count how many land within 3 px of their match. After 500 rounds I keep the biggest set of inliers and run computeH on all of them, which is the same least squares as Part A, just with way more points. Then the mosaic is just Part A's blend_image with that H.

Weill Hall had the most inliers, 112 out of 200, and the atrium had the fewest, 24 out of 154, because of all the repeated railing bars. In the side by side, the automatic mosaics for the outside of Gateway and Weill Hall look about the same as my manual ones, it's hard to see any difference. My clicked points land about 5 to 6 px off under the automatic H.

B.5Bells & Whistles: Panorama Recognition and Rotation Invariance (CS280A)

For bells and whistles I did panorama recognition. I took all 10 of my photos, including the bulletin board and MLK sign from the rectification part as decoys, and shuffled them, so the code doesn't know which ones go together. Then we run the whole pipeline on every pair, 45 of them, and keep a pair if it has at least 20 inliers and the homography looks like a real one, more on that below. Accepted pairs get linked, and linked photos go in the same group, so atrium 1 and atrium 4 end up together even though they barely overlap, since they connect through 2 and 3. For each group I pick the photo with the most links as the reference, chain the homographies out from it like in A.4, and stitch with multiMosaic.

It found exactly the 3 panoramas, and the bulletin board and MLK sign stayed on their own. So the 4 photo atrium panorama here is fully automatic, no clicked points at all, which is honestly pretty nice after how hard it was to pick those points by hand.

The Fake Match

Just counting inliers wasn't enough. Gateway outside 1 and atrium 1 got 20 inliers, which is almost as many as the real atrium neighbors, which had 26 and 27. But the homography for this fake match squashes the whole atrium photo down to almost a single line on Gateway, and a bunch of matches happen to sit along that line, mostly on repeating edges like railing bars and door frames. You can see it here, most of the atrium points land on the same spot on Gateway.

To catch this, I also check the determinant of the top left 2x2 of H, which is roughly how much it scales area. Real neighbors were between 0.3 and 3, and the fakes were basically 0. So a pair only counts if it has at least 20 inliers and the determinant is between 0.25 and 4.

def samePanorama(H, inliers):
    det = np.linalg.det(H[:2, :2])
    if len(inliers) < 20:
        return False
    if det < 0.25 or det > 4:
        return False
    return True

def matchAllPairs(points, descriptors):
    n = len(points)
    links = np.zeros((n, n))
    homographies = {}
    for i in range(n):
        for j in range(i + 1, n):
            match1, match2 = matchFeatures(descriptors[i], descriptors[j], points[i], points[j], 0.7)
            if len(match1) < 4:
                continue
            H, inliers1, inliers2 = ransac(match1, match2, 500, 3)
            if samePanorama(H, inliers1):
                links[i, j] = len(inliers1)
                links[j, i] = len(inliers1)
                homographies[(i, j)] = H
                homographies[(j, i)] = np.linalg.inv(H)
    return links, homographies
def groupPhotos(links):
    n = len(links)
    labels = []
    for i in range(n):
        labels.append(i)

    for i in range(n):
        for j in range(n):
            if links[i, j] > 0:
                old = labels[j]
                new = labels[i]
                for k in range(n):
                    if labels[k] == old:
                        labels[k] = new

    groups = []
    for label in range(n):
        members = []
        for k in range(n):
            if labels[k] == label:
                members.append(k)
        if len(members) > 0:
            groups.append(members)
    return groups
def stitchGroup(members, images, links, pair_homographies):
    reference = members[0]
    for k in members:
        if np.sum(links[k] > 0) > np.sum(links[reference] > 0):
            reference = k

    homographies = {reference: np.eye(3)}
    added = True
    while added:
        added = False
        for a in members:
            for b in members:
                if a in homographies and b not in homographies and links[a, b] > 0:
                    homographies[b] = homographies[a] @ pair_homographies[(b, a)]
                    added = True
                    

    group_images = []
    H_list = []
    for k in members:
        group_images.append(images[k])
        H_list.append(homographies[k])
    return multiMosaic(group_images, H_list)

Rotation Invariance

I also made the descriptors rotation invariant. My normal patches are always lined up with the image axes, so if you tilt the camera, the same corner gives a totally different patch. To fix that, for each corner I blur the image and take the gradient at the corner, which is the direction the brightness increases fastest, and rotate the 8x8 sampling grid to line up with it. The rotated points don't land on pixels anymore, so I sample with the same bilinear function from Part A. If the photo is rotated, the gradient rotates with it, so the patch comes out the same.

To test it, I rotated Weill Hall photo 2 by 30 degrees with my own warp function and tried matching it against photo 1. With the normal descriptors, only 17 matches made it through the ratio test and RANSAC found 6 inliers, so the pair gets rejected. With the rotated descriptors, there were 133 matches and 77 inliers, so it's a clean match. On the unrotated pair they do a little worse than the normal ones, 93 inliers vs 112, since the angle adds some noise, but that's still plenty.

def rotateImage(image, degrees):
    angle = np.radians(degrees)
    R = np.array([[np.cos(angle), -np.sin(angle), 0],
                  [np.sin(angle), np.cos(angle), 0],
                  [0, 0, 1]])
    rotated, offset, mask = warpImageBilinear(image, R)
    return rotated.astype(np.uint8)
def getRotatedDescriptors(gray, points):
    patch_blur = 2
    gradient_blur = 4.5
    window_half = 20
    spacing = 5
    first_offset = -window_half + spacing / 2
    border = 30

    smooth = gaussian_filter(gray, patch_blur)
    gradient_y, gradient_x = np.gradient(gaussian_filter(gray, gradient_blur))
    height, width = gray.shape

    kept = []
    descriptors = []
    for i in range(len(points)):
        x = points[i, 0]
        y = points[i, 1]
        if x < border or y < border or x >= width - border or y >= height - border:
            continue

        angle = np.arctan2(gradient_y[y, x], gradient_x[y, x])
        cos_angle = np.cos(angle)
        sin_angle = np.sin(angle)

        patch = np.zeros((8, 8))
        for row in range(8):
            for col in range(8):
                offset_x = first_offset + col * spacing
                offset_y = first_offset + row * spacing
                sample_x = x + cos_angle * offset_x - sin_angle * offset_y
                sample_y = y + sin_angle * offset_x + cos_angle * offset_y
                patch[row, col] = bilinear(smooth, sample_x, sample_y)

        patch = (patch - patch.mean()) / patch.std()
        kept.append(points[i])
        descriptors.append(patch.flatten())
    return np.array(kept), np.array(descriptors)
def getRotatedFeatures(image):
    gray, corners, strengths = getCorners(image, 3000)
    points = anms(corners, strengths, 500)
    return getRotatedDescriptors(gray, points)
